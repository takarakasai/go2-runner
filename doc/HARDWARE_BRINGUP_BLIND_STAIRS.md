#### ホスト側の線を機体なしで当てた（2026-11-21、§119 E.9 の続き）

**機体が無くても 3 要件のうち (3) は当てられ、(1)(2) が未であることも当てられる。**

| 読んだもの | 結果 |

| `ip -brief link show` | **有線は `eno1` 1 本だけ**（**別名 `enp8s0`**）。`<NO-CARRIER,BROADCAST,MULTICAST,UP>` state **DOWN** = **旗は UP だがケーブルが挿さっていない** |

| **現状で打ったときの出力** | `go2-run: eno1: does not match an available interface.` + `エラー: DDS participant: … failed: -1` **rc=1** —— **「線の段の診断」の 1 行目と文言ごと一致**（原因は **(b) アドレス無しと (c) link down が同時**） |

**当日の手**（ケーブルを挿してから。**`ip addr add` は使わない** —— NM が管理する
インタフェースでは再接続・再起動で消える）:

```bash
ip -brief link show eno1          # NO-CARRIER が消えて LOWER_UP になったか
ping -c 20 -i 0.01 <機体の IP>     # 機体のアドレスはここで確定する
# NM のプロファイルを作る（ipv4.never-default は**省略できない** ——
# 既定経路は無線が持っているので、奪うと外に出られなくなる）
nmcli con add type ethernet ifname eno1 con-name go2 \
    ipv4.method manual ipv4.addresses 192.168.123.222/24 \
    ipv4.never-default yes ipv6.method disabled
nmcli con up go2
ip -brief addr show eno1          # UP と 192.168.123.222/24 の両方を見る
```

> **`192.168.123.222` は仮**。機体側のアドレスを `ping` で確定してから
> **同じ /24 の空きアドレス**に決める。衝突が無いことは上で確かめてある。

## 1. 走らせる前に決めておくこと

### 傾きの中止閾値 — **段差では上げる**
既定は 35° で即脱力。**段差は登りきる試行でも 50° を超える**
（MuJoCo 実測: 下り 200 mm で 39.8°、登り中は 50〜57°）。
35° のままだと**成功している登坂を中断する**。

| 場面 | 指定 |
|---|---|
| 平地のテレオペ | 既定（35°） |
| 段差 | `--tilt-abort 65` |

### 方位サーボ — **常に入れる** `--heading-hold 2 0.5`

go2_rl §94（20 cm × 10 段・幅 3 m、開始位置 4 通り、Rust 閉ループ）:

| 方策 | サーボなし | サーボあり |
|---|---|---|
| P | 4/4、横 0.77 m | 4/4、横 0.65 m |
| ~~ZC101~~（枠外） | **3/4、横 1.58 m**（幅 3 m = ±1.5 m を超えて落ちる） | **4/4、横 1.19 m、roll max 58° → 16〜26°** |

**配備の P でも方位サーボは必ず入れる** —— 平地でサーボ無しだと
横に 11.82 m 流れる（入れると 0.52 m、ランタイム 36 本の最大値、
go2_rl §119 A3）。段差では 5 治具で +60〜+79 再現している。
枠から外した ZC101 は入れないと幅 3 m の階段から横に落ちていた。

**注**: go2_rl の古い記述「方位サーボは段差で有害」は **50/80 mm** の段・初期
系譜の方策での実測で、**200 mm × 10 段には当てはまらない**（§94.4）。
蹴上げが 100 mm 未満のときだけ切る。

**n を増やして確定した（go2_rl §104・§108）**: 上の表は n=4 で「P は中立」に
見えていたが、4 種 × 3 点 × 36 条件 = **432 走行**で測ると **+60**（Python の
sim2sim）／**+79**（この `policy --sim`）。帯どうしが重ならない。
**P でも大きく得。** ついでに**速度入力の劣化耐性も丸ごと吸収する**
（遅延 100 ms・横バイアス 0.10 m/s・欠測 80 % がどれも床の中に戻る）ので、
実機で脚オドメトリを較正する手間は要らない。

### 速度チャネルのディザ `--odom-dither 0.05` — **既定 off のまま。困ったときだけ**

方策に渡る胴体速度 3 要素に白色雑音を足す。**sim2sim では 20 cm 段差が
+28/432** だったが、**この `policy --sim`（＝実機と同じ経路）で測り直すと
+2（帯の下限）／+9（平均）**（go2_rl §108、14 水準 × 432 走行）。

| | sim2sim | **policy --sim** |
|---|---|---|
| サーボ ON の帯 | 390〜395 | 405〜408（幅 3） |
| ＋ディザ σ0.05 | 423 | 410〜420（3 引き） |

代償は 2 つ: **輸送コスト +1 %**、**走行ごとのばらつきが 10 倍**
（サーボ ON のヌル 3 本の幅 1 に対しディザ 3 本の幅 10）。
**432 本の平均を取れる sim では得でも、1 本しか走らない実機では薄い。**

**使う場面**: 段差であと一歩届かないときに `--odom-dither 0.05` を足す。
σ は 0.02〜0.10 が同程度、**0.20 は帯の下（害）**。種を固定したいときは
`--odom-dither-seed N`。

### 緊急停止 —— **何を押すと何が起きるか**（2026-11-15 に塞いだ穴）

**監査でここが丸ごと書いていなかった**（A1）。しかも**書く前に穴が 1 つ
開いていた** —— `--no-keyboard` と信号（端末や ssh が落ちた場合）では
**即死して kp 25 のまま脚が突っ張って残っていた**。2026-11-15 に
`SIGINT` / `SIGTERM` / `SIGHUP` を `q` と同じ路に繋いだ（`install_signal_stop`）。

| 押すもの / 起きること | 結果 | 実測 |
|---|---|---|
| **`Ctrl-C`** / `q` / `Esc` | **伏せへ 2.5 s ランプ → 脱力**。rc=0 | 3.00 s で脱力（機体側 `kp 0.0`）|
| **`Ctrl-C` をもう一度**（伏せている間に） | **伏せを飛ばして即脱力** | 1 回目から **0.81 s** で脱力 |
| `SIGTERM` / `SIGHUP`（端末・ssh が落ちる、`systemd` が止める）| **`Ctrl-C` と同じ**（伏せて脱力）| 3.00 s で脱力 |
| **起動の 3 s ランプ中**の `Ctrl-C` | **即脱力**（まだ歩き出していないので畳まない）| 0.0 s で脱力 |
| 傾き・観測の途切れ・異常の連続 | **即脱力して中断**（従来どおり）| rc=1、脱力 |
| **線が両方向死んでいる**（ケーブル抜け・機体の電源断）| **中断は鳴るが脱力は機体に届かない** —— 脚は kp 25 のまま | 502 ms で中断・rc=1、機体側は最後まで `kp 25.0 kd 0.50`（§119 E.9 R6）|
| **LowState だけが止まった**（機体はまだ指令を受けられる）| **中断して脱力が届く** | 502 ms で中断・rc=1、機体側 `kp 0.0 kd 0.00`（§119 E.9 R7）|
| **`SIGKILL` / 電源断 / クラッシュ** | **脚は最後の `q_des` に固まったまま残る**（kp 25） | —— **こちら側では直せない** |

> **最後の行が運用上いちばん大事。** 機体は最後に受けた `LowCmd` を保持するので、
> **`policy` が「殺された」場合は脱力が送られない**。段の上でこれが起きると
> 脚を突っ張ったまま残る。
> - **`kill -9` を使わない。** 普通の `kill`（SIGTERM）で畳んで脱力する。
> - **線が死んだときの「脱力して中断」は意図の表明にすぎない。** 中断の文言が
>   出ても、線が**両方向**死んでいれば脱力は届かず、`SIGKILL` と同じ扱いになる。
>   **片方向なら届く**ので、**文言だけでは区別できない** —— 機体側で kp を見るか、
>   物理の手（機体の電源・E-stop）に移る（§119 E.9 で両極性を実測）。
> - **電源断に備える**: 吊るか、人が支えられる高さでしか段を登らせない。
> - 脚が固まったまま残ったら、**機体側の電源で落とす**（こちらから送る手は
>   無い。`policy` を起動し直して `Ctrl-C` でも脱力できるが、その間も脚は
>   固まっている）。

**予行で当てた**（2026-11-15、`go2-fake-robot`）—— 鳴るべき 5 例と、
**変わっていないことを確かめた 3 例**（`Ctrl-C` キー・`q` キー・中止の路）。
塞ぐ前は信号 3 つすべてで機体側が `lowcmd 0 Hz … kp 25.0 kd 0.50` を
最後まで報告していた（= 脚が固まる）。

### そのほかの保護（既にある）
- 観測異常・推論失敗が **10 回連続**で中断（**2026-11-15 から脱力も送る** ——
  それまでは最後の `LowCmd` が保持されて脚が突っ張ったままだった）
- **lowstate が 500 ms 届かないと脱力して中断**（2026-11-15 に追加。
  `--state-stale-abort-ms`、100 ms で 1 回警告。下の「観測が途切れたら」）
- **4 脚とも非接地が 300 ms 続くと警告**（2026-11-15 に追加。
  `--no-contact-warn-ms`。**警告のみ・中断しない**。足裏力センサが死ぬと
  脚オドメトリが恒等的に 0 を出す。下の「予行した機体の病」）
- **指令の可動域に対して実測が動かないと警告**（2026-11-15 に追加。
  `--track-win-s`、既定 1.0 s。**警告のみ・中断しない**。機体が lowcmd を
  捨てていると**配線もトピックも正常なのに脚が一切動かない**。
  下の「予行した機体の病」）
- `--duration S` で自動終了 → 伏せ姿勢へ 2.5 s ランプ → 脱力
- `q` / `Esc` / **`Ctrl-C`** / `SIGTERM` / `SIGHUP` で同上
  （**もう一度 `Ctrl-C` で伏せを飛ばして即脱力**。上の「緊急停止」を読む）
- `--vx-max V` で指令速度に追加の上限

### 速度推定器 — **実機で最初に疑うところ**
MuJoCo では**接地判定を接触力の大きさに直すまで**、階段で脚オドメトリの
偏りが −0.72 m/s になり、5 段で崩れていた（`src/stairs.rs` 冒頭）。

観測の胴体速度が階段で壊れる可能性が高い。平地で合っていても保証にならない

#### **観測が途切れたら脱力して中断する**（2026-11-15 に追加）

予行で見つけた穴: **`policy` は lowstate が途切れても止まらなかった。**
500 Hz の輪は `state_age() > 20 ms` で異常を数えるのに、50 Hz の推論が
成功すると計数が 0 に戻る（**古い観測は数値としては正常**なので推論は成功し
続ける）。実測で **12 s の走行中 475/601 推論 tick が 20 ms 超、最大
9508 ms = 9.5 秒前の観測でも中断しなかった** —— 実機なら**線が抜けた後も
500 Hz で脚を駆動し続ける**。

| 旗 | 既定 | 何をするか |
|---|---|---|
| `--state-stale-warn-ms` | **100** | 1 回だけ警告（新着が戻ると掛け金が外れる） |
| `--state-stale-abort-ms` | **500** | **即脱力して中断**（`--tilt-abort` と同じ路）。`0` で無効 |

**既定を変える必要は普通ない。** 予行の実測で古さは `<2 ms` が 448/451
（最大 3.8 ms）なので 100 ms は既に桁の外。中止を 500 ms（= 250 周期の
開ループ）に置いたのは、**一過性の途切れで階段の途中に寝かせない**ため。
走行の終わりに `古さの見張り: … 古いまま続いた事象 N 回` が必ず出るので、
**N > 0 なら線を疑う**（健全な走行では 0）。

> **射程は方策の輪だけ。** 既定姿勢へのランプ（起動直後の 3 s）と最後の
> 伏せは設計上もともと開ループなので見ていない。
>
> **行動が「伏せへランプ」ではなく「即脱力」なのは**、観測が無い状態で
> 2.5 s かけて脚を動かすと**実姿勢が分からないまま動かす**ことになるため。

**同じ家系の穴をもう 1 つ塞いだ**: 「異常が連続したため中断」の路は脱力を
送らずに抜けていた。機体は最後の `LowCmd` を保持するので**脚は最後の
`q_des` に突っ張ったまま**になる。`--tilt-abort` と揃えて脱力させた。

#### 予行した機体の病と、**起きたら手順書のどこを見るか**（2026-11-15）

**なぜ予行するか**: この手順書は速度推定器を「**実機で最初に疑うところ**」と
名指ししているのに、**壊れたときに何がどう見えるかを一度も見ていなかった**。
初接続の日に判断を組み立てるのは遅い。

| 病 | 予行での出かた | **実機で見るところ** | 自動で捕まるか |
|---|---|---|---|

**足裏力が死ぬのがなぜ重いか**: 盲目段差の契約は**歩容計画を持たない**ので
接地マスクを足裏力センサから作る。センサが常に 0 だと接地脚が無くなり、
脚オドメトリは**恒等的に 0** を出す。**観測 48 には胴体速度が入っている**ので、
**歩いている間ずっと「止まっている」と方策に教える**ことになる。
しかも `v=(0.00, 0.00)` は「静止している」とも読めるので、**運転者が
見落とす形**で出る。中断しないのは、4 脚非接地が転倒中にも起きるため
（行動の選択は運転者の判断に残す）。

> **古さのヒストグラムは位相で嘘をつく。** あれは「**推論 tick で**観測が
> どれだけ古かったか」= §103 の要求そのものを測るので、**50 Hz でしか
> 標本を取らない**。lowstate の周期が推論周期（20 ms）の約数だと位相が
> 噛み合い、**最良の位相しか見ない** —— 予行では lowstate **100 Hz** で
> 古さ**最大 0.0 ms**（= 完璧に見える）と出た。線は明らかに劣化している。
> **線の健康は `LowState 新着 M/N` と Hz で読む。2 行は別の問いに答えている。**

> **古さの見張りは「一定の遅延」に原理的に映らない。** `state_age()` は
> **届いた時刻からの経過**（= 到着間隔）なので、線が一様に遅れても間隔は変わらない。
> 実測（§119 E.9）: 片道 **120 ms**（`ping` で往復 240.015 ms と確認）の線で古さ
> **最大 0.0〜2.2 ms・警告 0 回**（30/120 ms × 保持/歩行の 4 引きすべて）。
> §103 の要求は「観測が 20 ms 未満の古さ」なので、**要求と見張りが測っている量が違う**。
> 一定の遅延は LowState だけからは時計合わせか往復が無いと観測できない
> （増えていく遅延なら `機体 tick の飛び` に出る）。
> **遅延を疑うなら `ping` で測る。見張りは答えない。**

> **損失は古さの警告を出さない。** 欠落 10 % で古さ最大 6.0 ms・警告 0 回・正常終了
> （10 % が 100 ms 続く確率は 0.1^50 ≈ 0）。**損失が映るのは `LowState 新着 M/N` と
> Hz** —— 欠落 10 % で 448 Hz（健全は 499 Hz）。

> **予行の道具の限界も測った**: `--rate` を 100 以下にすると
> `joint_vel_out_of_range` で中断するが、これは**予行の関節模型が粗い**ため
> （`--follow-tc` を周期に合わせて 0.1 にすると通る）。**200 Hz までが
> 有効範囲**。ここで止まったからといって実機の周期の限界が分かった
> わけではない。

#### **脚が一切動かないとき** —— 疑う順（2026-11-15 に予行）

これは**最も切り分けにくい症状**で、配線もトピックも `LowState` も
正常なまま起きる。予行で順番を決めた。

1. **`sport_mode` が解除されているか。** 解除していないと機体側のサービスが
   モータを握ったままで、こちらの `lowcmd` は無視される。
   **解除は手動の手順ではなく、`policy` と `bridge` が接続時に自動でやる**
   （`src/backend.rs` の `release_sport_mode`。**`check` はやらない**）。
   だから見るのは「やったか」ではなく**「返ったか」**:
   - 成功すると log に `sport_mode を解除しました` が出る。**この 1 行を探す。**
   - 返らないと **8 s 詰まってから**
     `エラー: sport_mode release: RPC 1001 timed out after …` で落ちる
     （2026-11-15 に予行で実測）。**走り出す前に落ちる**ので、
     この文言が出たなら「解除できていないまま走った」ではない。
   - **`--no-release` を渡していないか。** 渡すと**何も印字せずに**解除を
     飛ばす。予行のコマンド列に入っているので、貼り間違いを最初に疑う。
   （以前の版はここに「手順 1」と書いていたが、**手順 1 は `check` で
   解除をしない** —— 存在しない手順を指していた。2026-11-15 の監査 A2）
2. **モータが servo mode か** —— `motor_state[*].mode` が `0x01` でなければ
   機体が受け付けていない（`GO2_TRACE_LEGS=1` の表で見る）。
3. **`lowcmd` の CRC** —— **これは最後に疑う**。予行で機体の立場から
   当て直して **6420/6420 一致**した（`go2-fake-robot --require-crc`）ので、
   こちらの CRC の流儀は線を渡っても通る。

**走行の終わりの「追従」行**がこの 3 つを 1 つの数字にまとめている:

```
policy: 追従（§119 E.5）: 指令が動いた窓 7（1.0 s ごと）、
        そのうち実測が動かなかった窓 0、可動域比の最小 0.68。
```

健全なら比は 0.5〜0.7。**0 に近ければ指令が機体に届いていない。**
`—（指令が動く窓が無かった）` は `--hold` では正常（指令が動かない）。

> **これは追従「誤差」の見張りではない。** 誤差に閾値を置くと誤爆する
> —— **階段では `|q_des − q|` が 4 rad 規模まで出るのが正常**（τ_ff の項）。
> 見ているのは**可動域の比**で、「指令は動いているのに実測が動かない」
> という**形**だけを拾う。だから**関節 1 本の死では鳴らない**
> （予行で比 0.57 = 健全と同じ。あれは `GO2_TRACE_LEGS=1` の仕事）。
> 条件は 12 関節**すべて**が止まっていること。

### 手順 3 の基準値（吊り・姿勢保持、sim、2026-10-31）

`--suspend` は sim では**胴体を 0.75 m で世界へ溶接する**（吊り台の代わり）。
実機では物理は変わらない — 変わるのは診断の出力で、`src/suspend.rs` が
関節ごとの関節速度・振動周波数・左右差を出す。**実機と sim で同じ関数**を
通すので数字がそのまま並べられる。

```
go2-run policy --model $M --hold --suspend --duration 12
```

**配備の P と枠から外した ZC101 で完全に同一**（`--hold` は方策を走らせないので当然だが、
一致を確認してある）。既定姿勢からのずれ [rad]:

| 関節 | ずれ | 関節速度 max | 振動 | 可動域 |
|---|---|---|---|---|
| FR / FL hip | **+0.049 / −0.049** | 0.00 | 0.0 Hz | 0.000 |
| FR / FL thigh | −0.017 | 0.00 | 0.0 Hz | 0.000 |
| FR / FL calf | +0.014 | 0.00 | 0.0 Hz | 0.000 |
| RR / RL hip | **+0.048 / −0.048** | 0.00 | 0.0 Hz | 0.000 |
| RR / RL thigh | −0.026 | 0.00 | 0.0 Hz | 0.000 |
| RR / RL calf | +0.011 | 0.00 | 0.0 Hz | 0.000 |

左右比 1.00、歩調差 0.00 Hz、追従誤差 max 0.049 rad、起動の蹴り 0.06 rad/s。

**この段が最も敏感な配線検査である理由**: 吊りは荷重がほぼ無いので
**実測関節角 ≈ `q_des`**（ずれ 0.05 rad 以内）になる。接地する手順 5 では
自重で `q_des` から 0.25 rad ずれる（既定 calf −1.50 に対し実測 −1.75）ので、
関節順や符号の食い違いが自重の変形に埋もれる。吊りでは埋もれない。

見るべき点:
- **hip のずれは左右で符号が逆、大きさは同じ**。どちらも 0 へ向かう（= 脚が
  真下へ垂れる）。揃っていたら左右が入れ替わっている。
- 大きさ 0.049 rad は Kp 25 と脚の自重の釣り合いそのもの（脚質量 ≈ 1.5 kg ×
  腕 0.08 m / 25 ≈ 0.048）。**実機でここが 2 倍違えば Kp か質量が違う。**
- 振動は 0 Hz。**唸るなら接地させてはいけない** — 空荷の脚は接地時より
  唸りやすい側なので、ここで静かでなければ接地でも静かにならない。

### 手順 4 — 吊って方策を走らせる（**歩容は出ない**）

**手順 4（2026-11-17 より前は手順 5）の旧い合否「歩容が出る / 左右が揃い異常な速さでない」は誤り。**
2026-10-31 に sim で予行して判った: **盲目契約の方策は吊ると歩かない。**

| 方策 | 指令 | thigh の歩調/可動域 | 定常の関節速度 max | 起動の蹴り |
|---|---|---|---|---|
| P | 0 | **0.00 Hz / 0.000 rad** | 0.00 | 8.9 rad/s |
| P | 0.3 | **0.00 Hz / 0.001 rad** | 0.01 | 9.0 rad/s |
| P | 0.6 | **0.00 Hz / 0.011 rad** | 0.01 | 9.0 rad/s |
| ~~ZC~~（枠外） | **0** | **1.5〜2.5 Hz / 0.41〜1.24 rad** | **24.6** | 15.7 rad/s |
| ZC | 0.3 | 0.00 Hz / 0.002 rad | 0.01 | 4.1 rad/s |
| ZC | 0.6 | 2.2〜5.5 Hz / 0.15〜0.37 rad | 9.8 | 5.9 rad/s |

理由は契約にある: 観測の先頭 3 要素は**接地脚オドメトリの体速度**で、
接地脚が無ければ 0 のまま動かない。方策は「0.3 を指令されているのに
0 しか測れない」状態を見続け、ずれた静止姿勢に落ち着く。歩容は接地が
作っている。**接地と同じ速度で振っているかを吊りで見ることはできない。**

**（枠から外した ZC101 の記録）ZC101 を吊って指令 0 で回してはいけない。** 定常で関節速度 24.6 rad/s、
thigh の可動域 1.24 rad の振り回しが**止まらない**（支えている人の手の
すぐ横で起きる）。同じ ZC が指令 0.3 では静止するので、特定の指令で
入る振動であって「吊れば必ず暴れる」でもない。**吊って方策を回すなら
P・指令 0 の 1 通りだけ**にする。

**起動の蹴りは吊り特有ではない。** 接地でも同じ量を取ると（`GO2_TRACE_LEGS=1`）
ZC 6.3 / P 12.3 rad/s で、吊り（15.7 / 8.9）と同じ桁。**方策の 1 発目の
行動そのもの**なので、接地でも起きる。手を離す前に一度見ておく値。

したがって手順 4 で言えるのは 2 つだけ:
1. 起動の蹴りが上の表の桁に収まっている（**数十 rad/s なら止める**）
2. 8 Hz を超える持続振動が無い（あれば低レベル側の問題。手順 3 へ戻る）

## 3. 中止したら

`--hold` に戻して観測を見る。傾き中断なら閾値の設定ミスを疑う（段差で 35° のまま）。
観測異常が続くなら DDS の取りこぼしか関節順の食い違い。

**`エラー: sport_mode release: RPC 1001 timed out after 8.0…s`** なら、
**走り出す前に落ちている**（脚は動いていない）。`policy` / `bridge` は接続時に
sport_mode の解除を自分で投げるので、**機体側の MotionSwitcher が応答して
いない**ということ: 機体の電源・`GO2_IFACE`・機体側のアプリの状態を見る。
**8 s 待たされてから落ちる**ので、固まったように見えるのは正常。
（2026-11-15 に `go2-fake-robot` で実測。あれは MotionSwitcher を持たない。）

**`LowState が … ms 届いていません — 脱力して中断しました`** なら線が死んだ
（2026-11-15 に追加した見張り）。閾値ではなく**線を**見る: `GO2_IFACE`、
機体の電源、ethernet。**関節順は予行で確認済み**なのでここでは疑わない。
走行の終わりの `古いまま続いた事象 N 回` は中断しなかった走行でも出るので、
**N > 0 の走行の数字は信用しない**。

**関節順・符号を疑うなら吊りへ戻る**: `--hold --suspend` は荷重がほぼ無く
実測 ≈ `q_des` になるので、接地したままの `--hold` より 5 倍敏感
（ずれ 0.05 rad 対 0.25 rad）。手順 3 の表と突き合わせる。

**脚が唸るなら** `GO2_TRACE_LEGS=1` を付けて走らせ、どの関節が何 Hz で
振動しているかを見る（接地でも吊りでも同じ表が出る）。8 Hz 以上は
歩容ではない。

**関節 1 本が死んでいるなら**同じ表の **可動域が 0.000・`|dq|max` 0.00** に
出る（左右差の行では **可動域比 0.00**）。**走行は正常に終わるので、表を
見なければ気づかない。**

**推定速度が `v=(0.00, 0.00)` のまま**なら足裏力センサを疑う（止まって
いるのではなく**推定が死んでいる**）。走行の終わりの「接地」行で
4 脚非接地の % を見る。
**ただしこの見え方は 2 通りある** —— 脚が実際に動いていないときも
`v=(0.00, 0.00)` になる。**先に「追従」行の可動域比を見て切り分ける**:

| 接地（4 脚非接地 %） | 追従（可動域比） | 読み |
|---|---|---|
| 100 % | 0.5〜0.7 | 足裏力センサが死んでいる（脚は動いている） |
| 0 % | 0.00 | **機体が指令を捨てている**（脚が動いていない） |

**`指令が機体に届いていません`** と出たら、疑う順は
**sport_mode の解除 → `motor_state[*].mode` が `0x01` か → CRC**。
CRC は最後 —— 予行で機体の立場から当て直して 6420/6420 一致している。
**sport_mode は「解除したか」ではなく「`sport_mode を解除しました` の 1 行が
出たか」と `--no-release` を渡していないかを見る**（上の「脚が一切動かない
とき」を読む。解除は `policy` / `bridge` が自動でやる）。

## 4. 方策の枠（2026-10-08、**2026-11-08 に 1 本へ**）

**なぜ 2 本目を検討したのか**: 段差用（P）と平地省エネ用（E）は
**原理的に両立しない**。
段を越えるには脚を上げるしかないが、省エネには下げたい。go2_rl で 7 軸試して、
目標条件（20 cm × 10 段）を落とさずに両立できたものは無かった
（`doc/go2_stairs_baseline_20260923.md` §77-§79）。

**契約は同じ**（観測 48 / 行動 12 / Kp 25・Kd 0.5）なので、**入れ替えは
ONNX の差し替えだけ**で済む。

### この手順書の「床の N 倍」の読み方（go2_rl §119 T.3 / T.4 / X.1 / V2）

**床 ≡ 2.059 × σ̂**（σ̂ = ディザの引きをまたいだ SD ÷ c4）。
以前の版は「引きをまたいだ範囲（max − min）」を床と呼んでいたが、
**範囲は引きの本数で尺度が変わる**ので 2026-11-13 に替えた。
**この手順書の倍率はすべて新しい定義に引き直してある。**

読むときの 3 つの注意:

- **0.8〜1.3 の倍率は「決まらない」と読む。** 床そのものが独立な
  引き替えで **24 %** 動く（go2_rl §119 T.4、独立な 2 組の 4 引きで実測）。
- **倍率には深さが付く。** この手順書の段差の倍率は**深さ 324**
  （開始点 12 点 × 27 × 引き 4 本 = 1 腕 1 面 1296 走行）。
  **深さが違う倍率は比べられない** —— 同じ主張が深さ 108 では 0.84、
  324 では 2.48 になった（§119 Y2。床は `1/√D` より速く落ちる）。
- **別の文書の倍率と直接は比べない。** 床は「腕の集まりの最大」なので、
  集まりを替えるだけで**中央 1.32 倍・最悪 2.19 倍**動く（§119 X.1）。
  倍率を引用するときは**どの面・どの引き・どの腕の集まり**かを添える。
- **まだ引き直していない数が 2 種ある**（下の表に残っている）:
  **比（床 ÷ 全幅）の列**と**生の床の値（「床 13 / 14」）**。
  どちらも腕の集まりを特定しないと引き直せない（§119 X.1）。
  **孤立障害の行だけは引き直し済み**（倍率 2.86・比 0.35。
  腕 3 本・引き 4 本・σ̂ の床。go2_rl §119 Z4）。
  **登りの行だけは別の 4 本で深さ 324 まで引き直してある** ——
  「登りの行は深さ 324 で変わった」の節を読むこと。
  **比は順位づけの判定には使わない**（badge 自身が籤 —— 3 引きの比の
  90 % 区間は [0.17, 0.57]）ので、判定は倍率の方で読む。

### 25 cm を超える段 — **登り切るが転ぶ**（go2_rl §119 S / G / G2 / K4 / M、2026-11-12）

上の表の登坂 **79 / 75** は「**どこまで登ったか**」の数で、床の内側だった。
**段 2 まで登った走行だけに絞って転倒率を見ると、高さで像が変わる。**

|---|---|---|---|
| **0.20 m（公称）** | **8.3 %** | 2.3 % | **2.48 倍** |
| 0.22 m | **14.7 %** | 3.5 % | **3.93 倍** |
| 0.24 m | **23.8 %** | 6.0 % | **2.97 倍** |
| 0.25 m | **29.8 %** | 8.3 % | **6.33 倍** |
| **0.26 m** | **38.5 %** | 15.6 % | **2.72 倍** |

各点の分母（段 2 に到達した走行数）は最小 **285**（深さ 324 = 開始点 12 点
× 27 × 引き 4 本。go2_rl §119 Y2 / Z2、1 腕 1 面 1296 走行）。
**P の値は深さを 3 倍にしてもほとんど動かない**（最大 1.4 ポイント）が、
**倍率は 5 点すべてが床の外になった** —— 床が `1/√D` より速く落ちたため。

> - **転倒率に「段」は無い。蹴上げについて滑らかに増える** ——
>   **配備している P では 1 cm あたり約 5 ポイント**
>   （公称 8.3 % → 26 cm で 38.5 %）。
>   **「ここまでなら安全」という高さは無い。**

>   同じ治具で測った他の 3 腕は **1 cm あたり 1.9 / 2.5 / 3.4 ポイント**で、
>   **P が測った 4 本の中で最も急**（3 本すべてに対して同じ向き）。
>   P は次に急な腕の **1.43 倍**。機体を替えずに方策を替えれば傾きは変わる。
>   **床の外と言えるのは 3 本のうち 2 本に対して**（深さ 324 で
>   LADMLP404 **2.58** / MOE202 **2.05**）。**ZC202 に対してだけ
>   決まらない（1.24）。**
>   **決まらない理由は床ではなく差の側** —— 互いに素な開始点の 3 組で
>   引き直すと、**ZC202 の傾きだけが自分の床より大きく動く**
>   （3.00 / 3.41 / 3.86。go2_rl §119 Z）。P は測った 4 腕で最も安定
>   （3 組で 4.97 / 4.79 / 4.89）。組をまたいだ**独立な**床で読んでも
>   P − ZC202 は **1.33** なので、「決まらない」は 2 通りの独立な
>   見積りが一致した結論であって、床の籤ではない。
> - **公称 20 cm でも差はある**（床の **2.48 倍**）—— 深さを 3 倍買って
>   「内側」から出た。**「床の内側 = 差が無い」は 4 引き × 108 走行でしか
>   成り立たない主張だった**（go2_rl §119 Y2 / U）。
>   ただし**絶対値は小さい**（**8.3 % 対 2.3 % = 6 ポイント**）。
>   通過率は 95〜98 % で飽和したまま。
>   **この表の 38.5 % を 20 cm に当てはめないこと。**
> - **25 cm を超える段では、登り切ることと転ばないことが別** ——
>   配備の方策は登り切る方だが、**段 2 以降で 3 回に 1 回以上転ぶ**。
>   登った段数は転倒の有無を予測しない（相関 **+0.015**）。
> - **通過率の崖（0.25 → 0.30 m）を転倒率に持ち込まないこと。**
>   同じ区間で、通過率には段があり転倒率には無い ——
>   **2 つの尺度は別の機構を見ている**（登れるか／登る途中で転ぶか）。

> - **公称を超える高さの段では、段 2 より上で吊りを外さない。**
>   根拠は上の 38.5 % だけで、**吊りの有無を実際に比べた測定は無い。**

**この数字の射程**（狭い。広げて読まないこと）:
sim（MuJoCo・天端 28 m の治具）・方位サーボ ON・指令 0.6 ・
蹴上げ 0.20 / 0.22 / 0.24 / 0.25 / 0.26 のみ・**腕 4 本で取った床**。

| 差 ÷ 床 | **−0.44** | **1.86** | 1.11 | **1.99** | 1.04 |

→ **配備の公称 0.20 m では台帳は変わらない**（向きすら逆で、しかも内側）。
**この手順書の 2 対 1 のトレードオフは公称での話**である。
→ **公称を超える段を登らせるなら、ZC202 が有利な面が 1 つ増える**
（0.22 と 0.25 m）。**深さが 3 倍になって初めて出た判定** ——
以前の版は 1 つの集約値（床の 0.89 倍）で「決まらない」と書いていたが、
**集約は蹴上げごとの符号の反転を隠していた**（go2_rl §119 V2 / Z2）。
帯が重ならないことを根拠にしてもいけない ——
重ならない 4 対が床の 0.43〜2.64 倍に散った。

### 既定の起動コマンド

```bash
A=/path/to/go2_rl/artifacts
GO2_IFACE=eth0 go2-run policy \
  --model $A/go2_blind_stairs20_policy.onnx \
  --heading-hold 2 0.5 --tilt-abort 65 \
  2>&1 | tee -a ~/go2_bringup_$(date +%Y%m%d_%H%M%S).log
```

**`--model-alt` は渡さない**（配備は 1 本）。
平地の試験では `--tilt-abort` を既定（35°）に戻す。

**`tee` は予行で当てた**（2026-11-15）—— 挟んでも `q` キーは効き、
走行の終わりの 3 行まで全部ファイルに入る（`2>&1` を忘れると**状態行も
終わりの 3 行も残らない**。あれは stderr に出る）。

**`--vx-max` は段ごとに変える**（2026-11-15 の監査 D1）:

| 手順 | `--vx-max` | 理由 |
|---|---|---|
| 6（平地 0.3） | `--vx-max 0.4` | 初めて接地で走らせる段。指令より出ても 0.4 で止める |
| **7〜9（指令 0.6）** | **付けない**（契約のクランプだけ） | **`--vx-max 0.4` を付けたまま指令 0.6 を打つと 0.4 にクランプされ、基準値（手順 7 の真値 0.539）と比べられない** |

> **クランプされたことは端末で確かめられるが、2 行が食い違う**
> （2026-11-15 に予行で実測）。`--vx 0.6 --vx-max 0.4` で出るのは
>
> ```
> policy: --vx-max 0.40 — |vx| をこの値で抑えます
> policy: キーボード無効。vx=0.60 vy=0.00 wz=0.00 を保持      ← 0.60 と言う
> policy: t=   3.0s cmd=(+0.40,+0.00,+0.00) ...                ← 実際は 0.40
> ```
>
> **効いている値は状態行の `cmd=` の方**。「保持」の行は**クランプ前の
> 指令**を印字している。以前の版はこの表の代わりに
> `--vx-max 0.4` を既定の起動コマンドに入れたまま「平地の試験では
> `--tilt-abort` を戻す」とだけ書いていたので、**手順 7 を 0.4 で走らせて
> 基準値と比べる**ことになっていた。
**`--state-stale-*` / `--no-contact-warn-ms` / `--track-win-s` は渡さない**
—— 既定（古さ: 警告 100 ms / 中止 500 ms、接地: 警告 300 ms、追従: 窓 1.0 s）
でよい。走行の終わりに出る **3 行を毎回読む**:

| 行 | 健全な値 | 外れたら |
|---|---|---|
| `古いまま続いた事象 N 回` | 0 | iface / 配線 / 機体の電源 |
| `4 脚とも非接地 … %` | 0 % | 足裏力センサ（脚オドメトリが恒等的に 0） |
| `可動域比の最小` | 0.5〜0.7 | **0 に近ければ指令が届いていない**（sport_mode → モータの mode → CRC） |

**手順 6〜9 では `GO2_TRACE_LEGS=1` も付ける**（関節 1 本の死はそこにしか
出ない。追従の行でも鳴らない）。

### 運転者の方策切替 — **`m` キー**（2026-10-31 実装。**配備では使わない**）

> **配備は 1 本になったので、通常運転でこの節は使わない**（go2_rl §119 A3）。
> 機能はランタイムに残してある —— 2 本目を足す理由が出たときのため。

走行中に押すと、`last_action` と関節目標を引き継いで**歩いたまま**入れ替わる
（引き継がないと新しい方策が「直前に何もしていない」という嘘の観測を見る）。
切り替わると端末に `方策を入れ替えました -> ...` と出る。

sim での実測（平地、枠から外した ZC101 → P、方位サーボ ON）: 立位が
**0.31 m から 0.35 m へ連続に移り**、転倒・観測異常なし。
`m` キー自体も疑似端末で押して確認済。

**注意**: 立位高さが変わるので、**段差の途中で押さない**。平地で持ち替える。
2 本目を渡していないときは「`--model-alt PATH` で渡す」と出るだけで何も起きない。

### 使い方

```bash
go2-run policy --model P.onnx --model-alt E.onnx [--swap-at 8.0]
```

`--swap-at` は **`--sim` 専用の計測用**（指定時刻に入れ替える）。
**実機は `m` キー**（上記）。

### 引き継ぎ — ここを間違えると分布外になる

入れ替えでは出ていく方の **`last_action` と保持関節目標を引き継ぐ**
（`policy::hand_over` → `BlindController::adopt_state`）。
素の `reset()` で始めると `last_action` が 0 になり、
**新しい方策は「直前に何もしていない」という嘘の観測を見る**。
歩行中の切り替えでそれをやると分布外の入力になる。

**契約が違う方策どうしは引き継げない**のでエラーにしている
（黙って繋ぐと分布外のまま走る）。

### 測った滑らかさ（MuJoCo、平地 16 s、8 s で P → E）

| | 変位 | 最大 roll / pitch | 追従誤差 |
|---|---|---|---|
| P のみ | +8.24 m | 4.01° / 4.22° | 1.036 rad |
| **P → E 入れ替え** | **+8.75 m** | **3.95° / 4.22°** | 1.036 rad |

**姿勢の乱れは増えていない。** 切り替え後は E の省エネ歩容になり、
速度が 0.538 → 0.575 m/s に上がる。

### 未着手: 運転者が切り替える口

実機で `m` キーのようなもので切り替える口は**まだ無い**。
実機が無いと試せないので、**測れる `--swap-at` までで止めている**。
実機で使うなら先にそこを足すこと（`hand_over` はそのまま使える）。
